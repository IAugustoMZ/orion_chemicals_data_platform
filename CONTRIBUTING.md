# Contributing and developing

The engineering entry point. The product page is the [README](README.md); the rules are in
[harness/](harness/README.md); agents start at [AGENTS.md](AGENTS.md).

## Set-up

```bash
poetry install --with docs        # .venv/ with the sdd tool, the quality suite and MkDocs
poetry run pre-commit install     # local gates on every commit (ADR-0004)
git config user.name "Your Name"  # approvals record your git identity
git config user.email "you@example.com"
```

> If your shell exports `VIRTUAL_ENV` (some IDE terminals do), Poetry may install into that
> environment instead of `.venv/`. Check with `poetry env info --path`.

## Everyday commands

| Command | What it does |
|---|---|
| `poetry run sdd status [id]` | gate states of every dossier and the next step |
| `poetry run sdd rt [RTnn ...]` | print requirements from the catalogue (all of them without ids) |
| `poetry run sdd new "Title" --slug x --rt RTnn` | start a dossier from the templates (usually run by the agent, after we agree on the RTs) |
| `poetry run sdd new "Title" --slug x --rationale "why"` | start a dossier for work outside the catalogue (no RT applies) |
| `poetry run sdd approve <id> <gate> --as <member>` | approve a human gate (people only, at a terminal) |
| `poetry run sdd verify <id>` | run the full quality suite and record gate G5 |
| `poetry run sdd check` | consistency: dossiers, docs, logos, links, ADRs, generated files |
| `poetry run sdd sync` | regenerate README status, specs index, traceability, tool adapters |
| `poetry run pre-commit run --all-files` | the commit gates on every file |
| `poetry run pytest` | tests with coverage |
| `poetry run mkdocs serve` | the documentation site on http://127.0.0.1:8000 |
| `docker compose up --build docs` | the same site in a hardened container |

There is no Makefile on purpose: the commands above work identically on Windows, macOS and Linux.

## The rules in one screen

1. Work happens in a dossier, on its branch `spec/<id>-<slug>` ([lifecycle](harness/lifecycle.md)).
2. Governed files (code, tests, `docker/`, `compose.yaml`, `pyproject.toml`, `harness/`, agent
   configuration) are committed only after G4 passed; pre-commit enforces it.
3. Code follows [principles.md](harness/principles.md): clean architecture (import-linter),
   SOLID, docstrings everywhere, strict types, tests with the code.
4. Security follows [security.md](harness/security.md): no secrets, least privilege, validated
   inputs, hardened containers.
5. Documentation follows [documentation-standard.md](harness/documentation-standard.md) and the
   [upkeep matrix](harness/architecture-upkeep.md): ADRs, diagrams with official logos, READMEs,
   the teaching guide.
6. English only; Poetry only; Docker Compose only.

## Repository layout

```text
AGENTS.md            canonical instructions for coding agents (CLAUDE.md, GEMINI.md, .github/, .cursor/ point here)
README.md            the product page; status blocks generated by `sdd sync`
harness/             constitution, lifecycle, gates, standards, roles/, templates/, team.yaml, checks.yaml
specs/               dossiers: specs/<id>-<slug>/ with dossier.yaml and one artifact per phase
docs/requirements/   the requirements PDF, rt-catalog.yaml, traceability.md (generated)
docs/architecture/   architecture pages, deployment, decisions/ (ADRs), logos/registry.yaml
docs/learn/          learning path, primers/, glossary
docs/tutorials/      first feature, coding agents, documentation site
docs/research/       the research behind the harness
tools/sdd/           the sdd command: domain, application, infrastructure, bootstrap, interfaces
tools/agent_hooks/   the PreToolUse guard for coding agents (standard library only)
tests/               unit, integration and end-to-end tests
.agents/skills/      canonical Agent Skills; .claude/ .cursor/commands/ .github/prompts/ are generated
docker/              Dockerfiles (docs site today)
compose.yaml         the local runtime (Docker Compose)
mkdocs.yml           the documentation site
```
